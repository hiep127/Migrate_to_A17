Occupant-zone filter — likely conflated with an already-present feature

No evidence of a separate filter

What was checked

  • The original plan listed "occupant-zone filter" as a suspected customization.
  • Research found a real Nissan A14 feature nearby — occupant-zone/mirror-request cleanup on user reassignment — confirmed via diff, and confirmed already present in a17full today.

Resolves with: confirming with whoever used the term what specific behavior they meant, or searching CarOccupantZoneService.java if the term resurfaces in testing.
3

canSwapCallOrRingerClientRequest() — confirmed real gap, priority unconfirmed

Gap confirmed real; impact unknown

What was checked

  • The authoritative diff shows Nissan's blocked/pending-request matching path in CarAudioFocus.java calls canSwapCallOrRingerClientRequest(...); Google's android14-release only checks entry.getAudioContext() == requestedContext there.
  • Directly confirmed in a17full by reading the exact code: exactly one call site exists (line 307, in the focus-holders matching block, "Replacing accepted request from same client"). The blocked-request block (line 343, "Replacing pending request from same client id") does not call it — matches Google's stock form, not Nissan's.
  • The function itself already exists and is already used in the other path — this is a one-call-site gap, not a missing function.

What this means in practice — unconfirmed

Without this second call site, a call/ringer client request that is currently blocked (not yet holding focus) may be evaluated more strictly than one that's already a holder — e.g. a legitimate call-to-ringer swap might be rejected in that specific pending-request case. Whether this is user-visible was not determined.

Resolves with: tracing an actual call/ringer swap scenario through both paths, or finding a bug report matching the symptom. If load-bearing, it's a one-line addition mirroring the existing call site.

CarAudioContextInfo.equals() / hashCode() — real addition, purpose unconfirmed

Real, but no consumer identified

What was checked

  • The diff shows Nissan's CarAudioContextInfo.java has a full equals()/hashCode() (value-equality via ID, name, and ArraySet-based audio-attribute comparison) that Google's android14-release does not have.
  • No caller requiring this specific implementation (a Set/Map keyed by it, or an equality-asserting test) was identified — search did not extend to the full test suite or callers outside car/audio/.
Resolves with: searching the A14 fork's test suite and any Set/Map usage of CarAudioContextInfo for a real dependency. If none exists, this can likely be skipped rather than ported.
